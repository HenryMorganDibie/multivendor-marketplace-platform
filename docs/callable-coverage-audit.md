# Callable coverage — what is deployed, and what calls it

Generated by `scripts/audit-callable-coverage.js`. Re-runnable, so the numbers
are measured on demand rather than asserted.

Grouped rather than counted, because a raw total of uncalled functions cannot
tell anyone whether something is missing. A scheduled job has no caller by
design. An Admin Portal function has no caller because that portal has not been
built. A vendor-app function with no caller is a gap in something already
delivered. Those are three different facts and only the last is work owed.

## This audit was wrong twice before it was right

Recorded because a coverage audit that is quietly wrong is worse than none: it
turns an unexamined surface into a settled question.

**81 orphans first**, including `createInvoice`, `recordPayment` and
`repriceCart`, all definitely called. The pattern could not span the multi-line
type arguments the mobile code uses:

```ts
const send = callable<
  Record<string, unknown>,
  { success: true; paymentId: string }
>('recordPayment');
```

**Then 61, still over-counted.** The directory walker excluded `lib` to skip the
backend's compiled output, and skipped each client's `lib/` as well — real
source in the mobile app, and where shared call sites live. Caught because seven
functions were wired and the number moved by two.

## On the invoice flow and mock data

An earlier summary said the invoice flow has zero mock data imports. That figure
was measured across the ten Section 8 screens and is accurate for those. It was
then restated as covering the whole flow, which it does not.

`InvoiceContext` imports `mockVendor`, retains `SEED_INVOICES`, and uses
`AsyncStorage`. The accurate description is **backend-backed for real accounts
with dev-only fixtures**:

- `SEED_INVOICES` is behind `!stored && DEV_LOCAL_AUTH_ENABLED`, and
  `DEV_LOCAL_AUTH_ENABLED` is `__DEV__` — false in every release build,
  including EAS preview and production. A shipped build cannot seed fixtures.
- `mockVendor` is used only by `generateInvoiceNumber`, on the local fallback
  path. The backend assigns the real invoice number.
- `AsyncStorage` holds the demo-login list. The context exposes
  `backendInvoices ?? local`, so a real account never reads it.
