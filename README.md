# Platform Backend

Firebase backend for the Platform multi-vendor marketplace, plus the Next.js frontend that consumes it. This repository covers four numbered milestones (Auth/Users/Vendors/Verification; Catalog/Orders/Inventory/Payments/Receipts; Commerce Chat/Notifications/Blocks/Pickup Auto-Send/Support Tickets/AI Help Placeholder/Chat Moderation; Vendor Subscriptions/Plan Gating/Ratings/Invoices) plus a fifth completed unit of work, the **Landing Page, CMS & Vendor Portal** package (provider-neutral checkout plus the public site, CMS, and vendor web portal built on top of it). That package is deliberately *not* called "Milestone 5" anywhere in this repo — the client's own numbering reserves **Phase 5** for the separate, not-yet-started Admin Web Portal, and reusing "5" for both would be confusing once that phase starts.

## Payment Requests — current spec and contract

Payment Requests was built against a spec the Founder wrote on 2026-08-31, quoted here for reference:

> For MVP, I don't want a manual admin approval workflow for payment methods. A vendor should be able to set one current payment method at a time: Bank transfer, or Cash. If they choose bank transfer, they enter their bank/payment instructions and confirm that the information is correct and belongs to them/their business. Once they save/confirm it, that becomes their active payment method and can be used immediately in payment requests. It does not need to sit in an admin queue waiting for a Platform team member to approve it. If they replace their payment method later, the new saved method becomes the current active method. We don't need a vendor-facing list of multiple saved methods for MVP. Also, I don't think we should call the method "approved" in the product if Platform isn't actually verifying ownership of the bank account. "Active," "confirmed," or "saved" would be more accurate. So for Send Payment Request, the vendor's current active payment method should be shown automatically. There doesn't need to be a payment-method picker if only one can be active at a time. One important thing: if the vendor hasn't set up a payment method yet and taps Send Payment Request, the app should tell them they need to set one up first and direct them to the appropriate setup screen rather than allowing a broken/no-op action. And just to keep the MVP distinction clear: recording/confirming that a customer has paid is separate from the vendor's saved payment method. Saving bank details does not itself mean Platform has verified or processed the customer's payment.

What's built follows this closely: no admin-approval queue, one active `paymentInstructions` value at a time (`vendors/{vendorId}/settings/payment`), an ownership-confirmation attestation required on first save, activates immediately, status labels read "Active"/"Confirmed" rather than "approved," `sendPaymentRequestInChat` reads the current instructions automatically with no method selection, and directs the vendor to set one up first if it's missing rather than failing silently. The one difference from the wording above is the "Bank transfer, or Cash" type choice — what's built is a single free-text field covering either, not a type selector.

Current contract: `updateVendorPaymentInstructions` accepts one field, free text, capped at 200 characters — no bank name, account number, or type flag. Adding structured fields or a type selector would be a real schema and callable change; full detail is in the "Payment requests & payment instructions" section below.

Separately, a structured "Payment Method" system (bank/cash type selection, an admin-approval change-request flow, change history) was priced independently at ₦120,000, later ₦165,000, shown to the Founder but not yet agreed or paid. It's distinct scope from Payment Requests.

The same note, written for whoever is touching the frontend screen, is at the top of `multivendor-marketplace-mobile`'s README.

The Storage emulator is required for all five suites. Milestone 1 exercises real file upload tests against Storage security rules (MIME allowlist, size limits, ownership, admin-only raw read). Milestones 2-4 use it for verification document setup during test provisioning; Milestone 4 additionally uses it for invoice branding logo upload validation.

Each suite provisions its own test accounts and vendor with a timestamped, unique identifier, so all five suites can be run independently and repeatedly without collisions. Milestone 4's webhook-related tests additionally generate a per-run identifier (`RUN_ID`) baked into every simulated Paystack event ID, so re-running the suite against an already-live (not restarted) emulator never false-triggers idempotency dedup from a prior run.

**One script per milestone, no separate demo script.** Milestone 4 used to ship a second, non-asserting `milestone4-workflow-demo.js` alongside the real acceptance suite — same subscription workflow, two files to keep in sync during integration. It's been folded into `milestone4-acceptance-tests.js` as Section 15: a single end-to-end vendor journey (signup → checkout → Paystack webhook → invoice → PDF → cancel → reactivate → admin override) that prints the real request/response payload at every step *and* asserts on it, so a broken step fails the run instead of just printing wrong data. `node milestone4-acceptance-tests.js` is now the only command needed for both the pass/fail suite and the readable walkthrough.

## What each milestone covers

**Milestone 1** establishes identity and access: Firebase Auth with custom claims for `customer` / `vendor` / `admin` roles, vendor registration and the verification submission flow, a five-tier admin role system (`super_admin`, `verification_admin`, `support_admin`, `safety_admin`, `read_only_admin`), and the Firestore and Storage security rules that everything else depends on.

**Milestone 2** builds commerce on top of that identity layer: vendor catalog management with server-enforced plan limits, cart pricing that the backend computes authoritatively rather than trusting the client, the full order lifecycle from placement through completion, a 48-hour vendor acceptance SLA, payment proof submission with abuse limits, and receipt generation.

**Milestone 3** adds real-time communication and customer support capabilities: a single persistent commerce thread per customer/vendor pair (not per order — new orders inject context into the existing thread), in-app and push notifications with quiethours and critical-notification handling, a block system with a documented active-order exception, fully automatic pickup-details delivery with no manual send path anywhere in the system, support ticket workflows, an AI-help placeholder surface intended for future assistant integration, and a rule-based chat moderation layer (below) that flags rather than aggressively hard-bans.

**Milestone 4** adds vendor monetization: a provider-agnostic subscription engine — live on Paystack and Flutterwave for Nigeria, and Stripe for international vendors — where Firestore is the single source of truth and no application layer ever reads a payment provider's API directly, a full plan-gating matrix enforced server-side across catalog limits, external orders, pickup automation, vendor settings, dashboard widgets, and business analytics, a ratings system with strict vendor-side anonymity (a vendor never learns which order or customer a rating came from), and invoices with plan-gated branding and PDF generation. See the dedicated sections below for the architectural decisions behind each.

**Landing Page, CMS & Vendor Portal** replaces per-provider checkout with a single provider-neutral flow: the frontend calls one `createSubscriptionCheckout({ plan })` callable, and the backend resolves the vendor's country (migration-safe: `businessLocation?.countryCode ?? countryCode`), selects a provider from a private country-specific priority list, and prevents double-billing on upgrade by cancelling the existing provider subscription before starting a new one. It also adds `getVendorSubscriptionOfferings`/`getPublicSubscriptionOfferings` (offerings + pricing, no provider names ever exposed to a client), renumbers invoices/receipts to `{VENDORSLUG}-{TYPE}-{seq}` (no padding, no year, immutable across slug changes), and implements the Price Change & Existing Subscriber Policy (existing subscribers keep their price until a real renewal charges the new one; 60-day notice is an operational/manual process, not backend-enforced — see `docs/LANDING_PAGE_CMS_VENDOR_PORTAL_MAPPING.md` Section 12.3). This package also built the `web/` frontend (landing page, CMS, Vendor Portal) and the handful of new callables it needed that didn't exist yet: `submitContactForm`, the `siteContent` CMS callables, `getVendorBillingHistory`, and `getVendorPortalAccess`.

**Frontend Phase 1** reduced vendor registration to seven fields. Business name, category and username are no longer asked for at signup: the system assigns a temporary username, and the rest is collected through the dashboard checklist, with publication gated on it instead. It also records what each user agreed to — the published version of each legal document, the consent wording that was on screen, and a server timestamp — read on the server so a client cannot claim a version it was never shown, and written once so republishing a document never alters an existing acceptance.

**Frontend Phase 2** implements catalog moderation as approved-live plus pending-revision. Editing a live item does not take it offline: customers keep seeing the approved version while the change is reviewed, and a refused change leaves the approved version untouched. Availability and stock apply immediately without review, because holding those for moderation would mean a vendor cannot mark something sold out. Four properties are covered by tests rather than by rules alone: a vendor cannot approve their own item or inject `moderationStatus` through an update, a pending item is refused by the cart rather than merely hidden from browsing, and the proposed revision lives outside the customer-readable document.

**The location catalogue** is now served rather than hardcoded. `listCountries`, `listStates` and `listAreas` read the 196-country catalogue, registration validates the selection server-side so no account can be created against a place that does not exist, and the three collections are readable but writable only by the importer. The app previously shipped 17 countries and 134 areas in its own source, so a vendor in any of the other 179 countries could not register at all.

**Sales counting** was corrected twice. It only incremented for items with inventory tracking switched on, which is off by default, so most items had a permanent sales count of zero however much they sold — and the Popular tag derived from it was silently wrong for every service and made-to-order vendor. Separately, vendor-recorded external orders counted as sales, which let a vendor manufacture their own Popular tag from numbers no second party ever saw. Stock still moves for an external order; the sales counter does not.

**Rate limiting** now covers the write endpoints. It previously existed on six files, none of which were the billing-sensitive ones. Fourteen callables across chat, order creation, external orders, invoices, support tickets, catalog changes, blocks and push token registration now enforce a per-minute ceiling, keyed on the caller and falling back to the IP for unauthenticated callers. Authentication alone does not prevent abuse: a signed-in user can call a write endpoint in a loop, and both Firestore writes and function invocations bill per call.

**Orders** run through the backend rather than local state. Placing one is two
calls, deliberately: `repriceCart` prices the basket against the live catalogue
and persists it, then `createOrderFromCart` turns that priced cart into an
order. There is no path that accepts a client-supplied total, because a total
that arrived from a device is a suggestion rather than a price. The vendor
lifecycle is `requested → accepted → in_progress → completed`; cancelling is a
customer action from `requested` or `accepted`, not a vendor one.

**Country availability** is now a condition of being discoverable, not only of
being able to order. It was previously checked when an order or conversation was
created, while `isDiscoverable` came from publication, verification and account
status alone. Closing a country therefore shut the front door and left the back
one open: every vendor there stayed listed, searchable and openable, and a
customer could browse them and fill a basket before being refused at checkout.

The country is now one of four conditions in the formula, in both the vendor
trigger and the sweep that runs when a country's availability changes, so the two
agree — an earlier attempt that only hid vendors on closure was undone by the
next write to any of those documents, which recomputed the flag from the other
three conditions.

`countryCode` and `country` are server-owned as a result. A security review found
that leaving them writable let a vendor hidden by a closed country set their
country to an open one with a single client write, reappear in discovery, resume
trading, and evade the closure sweep, which queries on that field. They are set
at registration and validated against the catalogue; a genuine relocation belongs
in an audited callable.

Because availability fails closed, per the instruction to reject safely when a
country is unknown, **every launched country needs an `ACTIVE`
`countryAvailability` record or its vendors are correctly but unhelpfully
invisible.** This belongs on the deployment checklist.

**Registration recovery** closes a dead end. Registration spans several writes, and `completeRegistration` used to reject every retry as "already finalized", so a failure between assigning the role and writing the vendor record left an account holding a vendor role with no vendor record — unable to finish, unable to start again, its email occupied permanently. It is now resumable: a finished account returns its existing record, a half-made one is completed. A daily sweep removes accounts that never came back after a 24-hour grace period, and an admin callable frees a specific address immediately. Neither will touch an account that completed registration. The client-side `deleteUser` remains as a fast path but is no longer the only way back, because it runs on the device that just failed.

**Order lifecycle and verification notifications** close a gap named in the Milestone 3 spec but never wired: a vendor accepting, rejecting, or completing an order never notified the customer, and a customer cancelling never notified the vendor. Same gap on the verification side — an admin's approve/reject decision updated the vendor's status but never told them it happened. Both now call `createNotificationInternal` at the point of the status change, using the same notification pipeline every other in-app notification already goes through.

**Catalog category deletion** replaces a client-only scaffold. `deleteCatalogCategory` checks vendor ownership, refuses to delete a system category, reassigns every item in the deleted category to uncategorized rather than leaving them pointing at a category that no longer exists, and writes an audit log entry — the same pattern every other admin/vendor-privileged mutation in this codebase follows.

**Malware scanning on uploads** runs a rule-based check before anything else touches a file: `onObjectFinalized` fires on every new object in the default Storage bucket, and only the five user-supplied content prefixes (`paymentProofs/`, `verificationDocuments/`, `vendorMedia/`, `invoiceBranding/`, `users/`) are actually sent to the scanner — invoice/receipt PDFs the backend generates itself are skipped, since they never originated from an untrusted client. Scanning runs against a private Cloud Run service running ClamAV (`services/malware-scanner/`), authenticated via the calling function's own identity token rather than a shared secret, so Cloud Run's IAM invoker check does the authentication.

Full request/response contracts for Milestones 1-4 are in `docs/frontend-contracts.md`; the Landing Page, CMS & Vendor Portal contract is `docs/LANDING_PAGE_CMS_VENDOR_PORTAL_MAPPING.md`.

## App Check Rollout

App Check is implemented as a monitor-mode helper (`functions/src/utils/appCheck.ts`) that records whether a valid App Check token was present on every sensitive callable, without blocking requests, controlled by the `APP_CHECK_ENFORCE` environment variable.

Planned rollout:

- **dev**: monitor mode only. App Check status is logged and recorded in audit logs; no requests are blocked.
- **staging**: monitor mode initially, switched to enforcement once the mobile app and Admin Web Portal both have App Check providers registered and have been confirmed sending valid tokens in real traffic.
- **production**: enforcement (`APP_CHECK_ENFORCE=true`) only after staging enforcement has run cleanly for a defined soak period with no unexpected rejections.

This sequencing exists to avoid a scenario where enabling enforcement before the frontend is ready locks out legitimate users. This remains an open item and should be treated as a prerequisite for general availability, not an optional hardening step.

## Verification document storage path

Canonical path, used consistently across Storage rules, the `recordVerificationDocument` callable, and the acceptance tests:

```
verificationDocuments/{vendorId}/{docId}
```

Vendor owners may upload (PDF or image, 15 MB max) but cannot read raw files back. Only admins can read uploaded verification documents directly; vendors see document metadata via Firestore (`vendorVerification/{vendorId}/documents/{docId}`).

## Contact card architecture (Milestone 3 decision)

Customer contact cards are stored on-device only, not in Firestore. There is no `users/{uid}/contactCards` collection in this backend. When a customer wants a vendor to have delivery contact details for a specific order, the frontend submits those details inline through `submitDeliveryContact`, which attaches an immutable, order-scoped snapshot to that one order. This snapshot cannot be resubmitted or edited once set, and a vendor's access to it expires automatically once the order reaches a terminal status, enforced through the `getOrderDetails` callable rather than raw Firestore reads. See `docs/frontend-contracts-phase-1.md` for the full contract.

This was a deliberate minimal-data-collection decision: it removes an entire class of PII exposure risk from the backend at the cost of contact details not syncing across a customer's devices, a tradeoff considered acceptable for the current stage of the product.

## Chat moderation (P3-FB-021)

A rule-based moderation engine runs inside `sendChatMessage`, `updateVendorChatSettings`, the quick-reply callables, and `createCatalogItem`/`updateCatalogItem` before anything is saved. It is deliberately a **flagging system first, not an aggressive hard-ban system** for chat: Platform does not process in-app payments in MVP, so ordinary commerce phrases like "bank transfer" or "call me" are never flagged on their own — they only count as evidence when they co-occur with a genuine off-platform-avoidance phrase such as "pay outside Platform" or "DM for price" in the same message. Catalog listings are held to a stricter standard than chat: a prohibited-item match in a listing's name/description always blocks the write outright, since there is no ambiguous "context" for a firearm or drug listing the way there can be for a chat message.

Rules are backend-managed config in the `moderationRules` Firestore collection (admin-only read, never client-writable), not hardcoded pattern lists baked into a function, and are bootstrapped via the idempotent `seedDefaultModerationRules` callable (`super_admin` only). Beyond keyword/phrase matching, several rules are regex-based to catch PII and off-platform contact patterns (phone numbers, emails, `wa.me`/`t.me` links, bare URLs, `@handles`) — these never block on their own but weigh into a cumulative per-user trust score. That score escalates a user's `accountStatus` (reusing the same enum every other access check already respects) to `frozen` at 50 points and `banned` at 100, transactionally, so concurrent flagged messages can't race past a threshold uncounted — escalation never reverses itself automatically; only `reviewModerationRestriction` (`super_admin`/`safety_admin`) can clear it or confirm the ban after human review. Every match also writes a `moderationEvents` record (hash + redacted snippet only, never the raw message) and, for chat, contributes to a per-thread `riskScore`. See `docs/frontend-contracts.md` for the exact error shapes and severity/action table.

## Vendor subscriptions & plan gating (Milestone 4)

The mobile app, admin dashboard, and vendor portal read subscription status exclusively from Firestore — no application layer reads from any payment provider API. `resolveEffectivePlan` is the single function every gated callable reads `PlanLimits` from; nothing gates off a hardcoded constant or a legacy field directly. Provider plan codes live in a separate, fully private `providerPlanCodes` collection (`allow read, write: if false` — Cloud Functions only, via the Admin SDK), completely isolated from the publicly readable `subscriptionPlans` document so a vendor-facing pricing page can never leak them.

**Three payment providers are live: Paystack, Flutterwave, and Stripe.** (Apple and Google are additionally scaffolded against the same abstraction but not yet live — see Apple & Google subscription backend below.) All three live providers converge on the exact same subscription state machine: `subscriptionWebhookCore.ts` holds the one implementation of staleness rejection, idempotency, distributed locking, out-of-order/priority resolution, and the `vendorSubscriptions` mutation itself — shared verbatim across `paystackWebhook.ts`, `flutterwaveWebhook.ts`, and `stripeWebhook.ts`. Each provider file's only job is verifying that provider's own signature scheme and mapping its payload shape into one normalized event object before handing it to the shared core.

**As of the Landing Page, CMS & Vendor Portal work, provider selection is no longer a frontend concern at all.** `createFlutterwaveCheckout`/`createStripeCheckout` are no longer public callables — they became internal-only functions (`runFlutterwaveCheckout`/`runStripeCheckout`) called exclusively by the single public `createSubscriptionCheckout({ plan })`, which resolves the vendor's country server-side and picks a provider from a private, country-specific `subscriptionProviderConfig` priority list. The frontend never selects a provider and never branches on one. Adding a new provider to a country means one new webhook handler plus a `providerPlanMapping/{countryCode}-{planId}` entry — zero frontend changes, and zero changes to `vendorSubscriptions`, `resolveEffectivePlan`, `PlanLimits`, or any plan-enforcement logic.

The three providers authenticate their webhooks completely differently, each handled correctly in its own file: Paystack and Stripe both use HMAC (SHA-512 and SHA-256 respectively, the latter also timestamp-tolerance-checked as Stripe's own replay-protection layer on top of this codebase's generic 24-hour staleness check); Flutterwave uses a static secret-hash string compared directly rather than computed, which is its documented scheme, not a corner cut here. Every path still gets the same before-any-Firestore-access ordering and the same out-of-order protection via an event-priority table plus timestamp sequencing — an event only applies if it's higher priority than the last-applied event, or equal priority with a later sequence number. That guard resets whenever an activation event carries a different provider subscription ID than what's on file, so a vendor who cancels (or migrates providers) can still resubscribe later — without that reset, a cancellation (the highest-priority event in the table) would permanently block every future activation webhook from ever being accepted again, a real bug caught and fixed by the acceptance tests before this was generalized from Paystack-only to all three providers.

**Deliberate deviation from the written spec**, documented in `functions/src/types4.ts`: vendor suspension reuses the existing Phase 1 `vendors/{id}.vendorStatus` field rather than a duplicate `suspendedAt` field on `vendorSubscriptions`, avoiding two sources of truth for the same fact. `resolveEffectivePlan` checks `vendorStatus` first, ahead of admin override and subscription status, exactly matching the spec's intended priority order.

Rate limiting (5 requests/60s, scoped per vendor per function) applies to every billing-sensitive vendor callable: `createSubscriptionCheckout`, `cancelSubscription`, `reactivateSubscription`, `updateInvoiceBranding`; `getPublicSubscriptionOfferings` and `submitContactForm` are rate-limited by IP instead, since they have no auth boundary at all. Admin actions (`cancelSubscriptionAdmin`, `applyManualSubscriptionOverride`) are not rate-limited but require a mandatory `reason` field and write a full before/after audit trail to `subscriptionEvents`, an immutable append-only log of every processed *and* ignored webhook event, tagged with which of the three providers sent it.

## Ratings & invoices (Milestone 4)

**Ratings** are star-only with an optional private feedback field, submitted once per completed order via `submitRating` and final upon submission — there is no customer-facing edit or delete path. The privacy model is strict: a vendor never receives `orderId`, `customerId`, or any order reference in any response, query, or export. The only identifier a vendor ever sees is a separately and randomly generated `displayId` (e.g. `R-K8F2M7`), not derived from any other identifier. This is enforced structurally, not just by convention — direct Firestore reads of `ratings` are denied to the vendor role entirely in `firestore.rules`, so the only way a vendor can read their own ratings at all is through `getVendorRatings`, a callable that projects the response shape server-side. `moderateRating` (admin-only) can hide or remove an abusive rating but never deletes the document, preserving a full audit trail and excluding it from `vendorRatingStats` recomputation going forward.

**Invoices** compute line-item totals server-side (a client-supplied total is never trusted), are gated by a monthly quota (`invoicesPerMonth`) tracked via a per-vendor-per-UTC-calendar-month counter sub-document — explicitly the UTC boundary, not the vendor's local timezone, to remove reset-logic ambiguity. Invoice branding (logo, brand color, thank-you message, footer, premium templates, QR code, print layout) is validated field-by-field against the vendor's plan before any write, with the logo checked against the real uploaded Storage object's content-type and size rather than trusting client-declared metadata. Marking an invoice paid captures a permanent `brandingSnapshot`, filtered through whatever plan was active at that exact instant — a later downgrade can never mutate a paid invoice's branding, matching the spec's explicit guarantee. `invoiceHistoryDays` governs `listInvoices` visibility only (`hiddenFromHistory`, flipped by a daily scheduled job), never a hard deletion deadline — paid invoices are financial records and are never automatically destroyed. Public "Share Invoice" links are served through `getPublicInvoice`, a callable rather than a direct Firestore query, since a raw client query by share token would let anyone enumerate the field and brute-force tokens against an open collection; the callable also revokes a cancelled invoice's public visibility before returning anything. PDF generation uses `pdfkit` (pure Node, no headless browser), a deliberate choice to avoid a full Chromium process's memory footprint in a Cloud Function for what's fundamentally a structured document.

## Promotions (Milestone 4)

Built 2026-07-23, before this README's previous update, and had been incorrectly listed under "Known gaps" as not yet built until this revision — a documentation error, not a code gap. A vendor manages promotions through `createPromotion`, `updatePromotion`, `deletePromotion`, and `togglePromotionActive`; `listVendorPromotions` serves the vendor's own management view. `evaluatePromotions` runs at checkout/cart-pricing time as part of the same trusted-server-side pricing path `repriceCart` already owns, rather than trusting a client-supplied discount. Promotions are readable on the storefront by the same `isDiscoverableVendor`/`isPublishedVendor` rule as the rest of a vendor's public catalog (`firestore.rules`), and writes remain Cloud-Functions-only.

## Payment requests & payment instructions (Milestone 4)

Payment requests were named in Milestone 4's scope but not actually built until 2026-08-30 — before that date, the vendor-facing "Send Payment Request" screen existed but sending one did nothing, a `console.log` and a fake success alert. `sendPaymentRequestInChat` is the real backend: a `paymentRequests` collection, rate-limited, App-Check-checked, vendor-role-only, cross-checked that the calling vendor owns both the order and the chat thread it's being sent into. The vendor names the amount themselves — legitimate input for their own order, validated against the order's real total — but everything else (customer identity, the payment instructions shown) is assembled server-side, never trusted from the client. Any prior still-active request for the same order is automatically superseded (`active` → `replaced`) so a customer only ever sees one live request per order. `submitPaymentProof` lets the customer upload proof (max 3 images, max 2 submission attempts before an automatic `LOCKED` state), routed through the same malware-scanning pipeline as every other user-uploaded file; `reviewPaymentProof` is the vendor's accept/reject side.

There is deliberately no structured vendor payment-method system (no bank name/account-number/account-type fields) anywhere in this backend — only a single free-text `paymentInstructions` string, gated by `paymentInstructionsEnabled` and an explicit ownership-confirmation attestation, written by `updateVendorPaymentInstructions`. This matches the client's own written spec for the feature (a vendor's current active payment method shown automatically on a payment request, no picker, direct the vendor to set one up first if it's missing, no admin-approval queue, never call it "approved" since ownership is attested, not verified) rather than a separate structured system, which remains unbuilt, priced separately, and outside this feature's scope.

**Security fix, 2026-09-18**: `paymentInstructions`/`paymentInstructionsEnabled`/`ownershipConfirmed` and their timestamps were originally written directly onto the `vendors/{vendorId}` document. That document is publicly readable, no authentication required, by any discoverable or published vendor's storefront (`isDiscoverableVendor`/`isPublishedVendor` in `firestore.rules`, neither of which checks `isSignedIn()`), and Firestore rules cannot filter individual fields on a document read — so a vendor's real payment instructions, potentially including real bank account details, were readable by anyone with the app's public Firebase config and no account at all. Moved to a private `vendors/{vendorId}/settings/payment` subdocument, owner-and-admin read only, matching the existing pattern already used for `settings/notifications`, `settings/chat`, and `settings/pickup`. `sendPaymentRequestInChat` and `updateVendorPaymentInstructions` both updated to read/write the new location; existing `platform-dev` vendor documents migrated. Verified live post-fix: an unauthenticated read of the public vendor document no longer contains these fields, an unauthenticated read of the new subdocument is rejected, and the full send-payment-request flow (an authenticated vendor owner reading their own settings, then successfully sending a request) still works exactly as before.

## Apple & Google subscription backend (scaffolded)

Structurally complete, following the same provider-abstraction contract as the three live providers (verify the provider's own signature/authentication scheme, map the payload into the shared `NormalizedWebhookEvent` shape, hand off to the one `subscriptionWebhookCore` implementation every provider converges on) — but neither is exercisable end to end yet, and both are explicitly scaffolded pending real store setup on the Founder's side, not partially working.

**Apple**: `appleServerApi.ts` sets up `AppStoreServerAPIClient` and `SignedDataVerifier` against Apple's own `@apple/app-store-server-library`, verified against Apple's real, downloaded Root CA G3 certificate for JWS signature-chain verification. `getOrCreateAppleAppAccountToken` mints a real UUID per vendor (StoreKit requires `appAccountToken` to be a UUID, not this app's own Firestore vendor ID) and stores the reverse mapping for the webhook to resolve. `verifyAppleTransaction` gives instant plan activation right after a purchase, fetching the transaction directly from Apple's API rather than trusting the client, processed through the same core the webhook uses. Notification verification tries the sandbox verifier first and falls back to production only on Apple's own `INVALID_ENVIRONMENT` signal, so sandbox testing and a live production listing can coexist without one silently rejecting the other's notifications. `PRODUCT_ID_TO_PLAN` uses the Founder's confirmed permanent convention (`com.platform.app.<plan>.monthly`); the private signing key is read only from `APPLE_IAP_PRIVATE_KEY` via Google Secret Manager, never a plain env var, since the Founder generates and owns that credential directly. Cannot run end to end without real `APPLE_IAP_KEY_ID`/`APPLE_IAP_ISSUER_ID`, real subscription products created in App Store Connect, and the mobile app's purchase flow passing `appAccountToken` at purchase time — none of which exist yet without a real EAS build.

**Google**: `googleServerApi.ts`/`googleWebhook.ts`/`verifyGoogleTransaction.ts` mirror the Apple integration's structure. Google's `obfuscatedAccountId` has no UUID format requirement, so the raw vendor ID is used directly at purchase time, no token-minting/reverse-lookup collection needed the way Apple's did. Two correctness bugs were caught and fixed before this ever ran against real traffic: `SUBSCRIPTION_CANCELED` means auto-renew was turned off, not that access was lost (the vendor keeps access until `SUBSCRIPTION_EXPIRED` — mapping it to `cancelled` would have cut off a vendor mid-period they already paid for), and Google reuses the same `purchaseToken` across an entire subscription's renewals, so idempotency is keyed on Pub/Sub's own per-delivery `messageId` instead, not `purchaseToken` + notification type. Cannot run end to end without a Play Console service account with the Play Developer API enabled and real subscription products created there.

Both are classified as already-paid Milestone 4 work, not new billing — the subscription engine's scope always included App Store/Google Play sync; only the store-side setup was blocked on the Founder.

## Admin MFA enforcement (Milestone 1)

Named in Milestone 1's accepted, already-paid scope. The schema fields (`mfaRequired`, `mfaEnrolled`, `lastMfaAt`) have existed since `acceptAdminInvite` was built, but nothing checked or used them until 2026-09-02. `beginAdminMfaEnrollment`/`confirmAdminMfaEnrollment`/`verifyAdminMfaCode` implement real TOTP-based enrollment and verification, with the secret stored in a new Cloud-Function-only `adminMfaSecrets` collection, never on `adminUsers` where any admin could read it. `assertAdmin` now enforces a fresh verification within a rolling window for any admin with `mfaRequired` set.

Enforcement is deliberately held behind `MFA_ENFORCEMENT_ENABLED` (currently `false`), documented in `docs/admin_mfa_enforcement_killswitch.md`. Every existing admin already has `mfaRequired: true`, but none has enrolled, since no Ops Console screen has ever called the enrollment callables — turning enforcement on before that screen exists would lock every admin out with no way back in except a manual Firestore edit. The enrollment/verification callables themselves are safe to use immediately regardless of the flag; only the reject-if-not-enrolled-or-verified half of `assertAdmin` is held back. Flipping it on later is a one-line change once the Ops Console has an enrollment screen.

## Fixes and hardening since 2026-08-26

The following were found and fixed after this document's previous update, mostly through direct client review and full-app audit passes rather than the original acceptance suites (which still pass as originally written — these are gaps the suites didn't cover, not regressions in what they did cover).

**Vendor settings & storefront.** `updateVendorSettings` never accepted `weeklyHours` at all, so no vendor's trading hours could ever be saved server-side, despite the mobile UI having called it with that field for a while. Fixed alongside two crash bugs that turned this into an opaque "internal" error rather than something a client could act on: `resolveEffectivePlan`'s cancelled-subscription check was missing a null guard present on the checks above it, and `updateVendorSettings` read `vendorId` off the auth token without checking it was present, so a stale token threw a raw SDK error instead of a clean rejection. `fulfillmentTypes` (pickup/delivery/shipping) is now also a real, validated, whitelisted field on the same callable, and `repriceCart` enforces it against the vendor's own enabled methods — an unconfigured vendor (every vendor before this shipped) is treated as not-yet-configured, not rejected. `updateVendorStorefront`'s Website/Instagram/TikTok links previously accepted any URI scheme at all (`javascript:`, `file:`, `intent:`, etc.) which the mobile storefront then opened directly; now every link must resolve to a real `http(s)` URL, and Instagram/TikTok links are verified to actually point at that platform's domain. `updateCatalogCategory` didn't exist at all — renaming a category only ever updated local state and reverted on the next snapshot.

**Orders.** `createOrderFromCart` minted a random order ID with no check for a cart that had already produced one, so a lost-response retry or a genuine concurrent double-submit could create two real orders from one cart; the order document is now keyed deterministically by `cartId`, with post-creation side effects (chat injection, notifications, audit logs) firing only once. The reject/cancel reason a vendor or customer provides is now persisted onto the order itself instead of being dropped after the notification fired. When a customer edits their own proposed change and a vendor accepts it, the customer's own edit now wins rather than an earlier snapshot. `getBusinessAnalytics`'s Top Customers metric counted every external order as a distinct one-off customer (external orders get a synthetic customer ID), pushing real repeat customers out of the Top 10 — the same function already guarded two sibling metrics against exactly this, this one had been missed.

**Auth & privacy.** `repairVendorClaims` re-issues vendor custom claims when Firestore already shows a finished registration but the ID token's claims are missing or stale (narrow by design — the only identity input is `request.auth.uid`, every value used is read back from Firestore records already verified to belong to that uid). `completeRegistration`'s retry fast-path no longer trusts Firestore's finished-registration state outright without also repairing the token if the original `setCustomUserClaims` call had failed. A customer's full name was leaking to vendors raw in `createCommerceConversation.ts` and `blockFunctions.ts` — the Phase 2 spec (`customerSnapshot.displayName = "Jane D."`) already meant a customer should only ever be shown to a vendor as first name + last initial, and `createOrder.ts` already did this correctly, but these two paths stored/exposed the untruncated field. Harmless in practice only because registration never collected more than a single last-initial letter to begin with.

**Chat.** `sendAwayMessageIfEligible` never actually consulted a vendor's configured `awaySchedule` (always / outside business hours / a custom window) — only `awayMessageEnabled` and the per-thread cooldown gated sending, so a vendor who configured "outside business hours only" still got away-messages fired at any hour. Fixed with `isAwayScheduleActive`, mirroring the client's own schedule-check logic; operates on UTC hours, a known and disclosed limitation, since no per-vendor timezone field exists to do otherwise.

**Subscriptions & billing (Landing Page/CMS/Vendor Portal audit).** Downgrades were re-billing a vendor immediately instead of scheduling a period-end transition as the spec required — `requestSubscriptionDowngrade`/`cancelPendingDowngrade` added, and the scheduled job now correctly cancels the old provider subscription instead of leaving it silently billing. Also fixed: the public contact form had no CAPTCHA or velocity-abuse challenge, CMS image uploads never enforced pixel dimensions or compression, and a `past_due` subscription had no distinct "payment failed" state or retry action.

**Performance.** Independent `await` calls in the hottest user-facing callables were running serially where nothing forced them to; parallelized, shipped free rather than the priced `minInstances` cold-start fix, which remains a deferred, costed, separate decision. A missing composite Firestore index on `orders` (`vendorId` + `createdAt` range) was found and added.

**Operational safeguard.** A CI check and a pre-deploy script now flag any commit reaching any branch of this repo from an identity outside the recognized set. Neither can block a push outright — this account has no branch-protection configuration access on the GitHub repo — but both surface it immediately: a failed GitHub Actions check plus GitHub's own notification, and a one-command manual check available before any deploy.

## Security posture

No system should be described as fully secure without qualification, and this backend is not an exception. The following reflects an honest account of what has been verified against and what remains open.

**What has been verified:** every Firestore collection carrying business-critical or sensitive data denies direct client writes and routes exclusively through Cloud Functions. Sensitive fields use narrow, allowlisted update rules rather than broad ownership checks — a user can mark their own notification read but cannot rewrite its title or body, for example. Authentication is delegated entirely to Firebase Auth rather than a custom credential store. Server-side business logic (block enforcement, country availability, order-state transitions) is re-validated on every relevant call rather than trusted from client state. All 390 acceptance tests across the five milestones include denial-path cases, not just success-path cases. See `docs/full-codebase-audit-2026-07-17.md` for the most recent full test run plus a codebase-wide authorization/rules/App-Check/rate-limit sweep.

**What remains open:** App Check enforcement, as described above, is not yet active. No independent, adversarial security audit has been performed on the deployed rules and Cloud Functions — everything here has passed rigorous self-review and automated testing, which is not equivalent to a third party whose sole objective is finding a way through it. One historical bug (a Firestore rules wildcard that unintentionally granted broader write access than intended to a subset of Milestone 3 settings documents) was found and fixed during Milestone 3 development; this raises the possibility, not yet ruled out, that a similar latent rule collision exists elsewhere in `firestore.rules`. A full manual pass through every `match` block, specifically checking for cases where a general wildcard and a more specific match both apply to the same path, is recommended before production launch. Request-size and payload-complexity limits are not uniformly enforced across every callable, which is a resource-exhaustion consideration even where it is not a data-integrity risk.

**Findings since, and what they say about the rules file.** Two rounds of review by the client, plus automated passes over both the frontend branch and the backend changes, found real defects. One bears directly on the recommendation above.

The client's review found four authentication faults in the mobile app, all valid. The worst: signing in to Firebase on a device with no local profile built a session with `role: 'vendor'`, `status: 'active'` and `onboardingComplete: true` all hardcoded, returning before the blocked-status check beneath it — so a customer signing in on a second device became a vendor, and a banned or frozen account became an active one. Alongside it, logout never called `signOut`, so the Firebase session outlived it; the stored session was trusted at launch with no revalidation; and a fixed OTP of `123456` with an on-device plaintext password store were reachable in any build. All are fixed, and the local paths are now refused outside development.

The automated review then found the predicted rule collision, in exactly the shape this section warned about. `vendorOwnerUpdateAllowed()` is a denylist rather than an allowlist, and `countryCode` was not on it. Once country availability became a condition of discoverability, that omission let a vendor hidden by a closed country write themselves into an open one, reappear in discovery, resume trading, and evade the closure sweep. Fixed by making `countryCode` and `country` server-owned.

The lesson is the one already recorded: **denylist rules fail silently as the schema grows.** `userUpdateAllowed()` uses an allowlist and would not have had this problem. Converting `vendorOwnerUpdateAllowed()` and any remaining denylist rules to allowlists is now a specific, named item rather than a general recommendation.

The backend pass then found a second instance of the same underlying mistake, in `cleanupOrphanedAccount`. It read `request.auth.token.role` directly instead of calling `assertAdmin()`, making it the only one of twenty-five admin callables not to. That matters because revoking an admin rewrites their custom claims but cannot revoke an ID token already issued, so a revoked admin holds `role: "admin"` for up to an hour; `assertAdmin()` re-checks `adminUsers/{uid}.status` on every call, which is precisely what closes that window. During it, every other admin callable would refuse them and this one — which permanently deletes accounts — would not. It also had no role scoping, so a support or verification admin held a capability that revoking an admin (`super_admin`) and suspending a vendor (`safety_admin`) both require a specific role for. Now uses `assertAdmin()` scoped to `super_admin`, with a short grace window so an account created moments ago, which is indistinguishable from an abandoned one, cannot be deleted.

**Both findings were the same class of error: bespoke logic written where a house pattern already existed.** A denylist that needed a new field remembering, and a hand-rolled claim check where `assertAdmin()` was already the convention. Neither was subtle once seen, and neither would have existed had the established helper been used. That is worth more as a review heuristic than either individual fix: when reading new code here, check first whether it reimplements something the codebase already does properly.

The three highest-priority items before general availability are App Check enforcement, an independent review of the Firestore rules file, and converting the remaining denylist update rules to allowlists.

## Known gaps / explicitly deferred

- Production monitoring dashboards and alerting are not part of this code delivery.
- App Check enforcement is deferred per the rollout plan above.
- Admin MFA enrollment/verification backend is now built (see Admin MFA enforcement section above), but enforcement is held off behind `MFA_ENFORCEMENT_ENABLED=false` — an Ops Console enrollment screen still needs to exist before it's safe to turn on, since no admin has enrolled yet.
- Country availability management is currently manual (a single document seeded directly in Firestore for Nigeria). Full admin tooling for managing country rollout is deferred to a later phase.
- Typing indicators and swipe-to-reply are not implemented in this milestone. Typing indicators would require provisioning Firebase Realtime Database alongside Firestore, since that is a better fit for high-frequency, ephemeral presence data than Firestore's per-document billing model. Swipe-to-reply is primarily a frontend gesture-handling concern; the backend would need a small, additive extension to the message schema to carry a reply reference.
- A moderation admin review queue UI/tooling is not part of this milestone. The backend produces everything a queue would need (`moderationEvents`, per-thread `riskScore`), but building admin-facing screens to act on them is Phase 5 scope.
- The following Milestone 4 items are explicitly deferred to post-launch, per the source spec's own scope table, not oversights: a subscription monitoring dashboard (active/past-due/grace-period/churn metrics), a disaster recovery runbook, a dedicated `subscriptionHistory` collection distinct from the append-only `subscriptionEvents` audit log, and an in-memory/Firestore-level cache for `resolveEffectivePlan` (deliberately uncached for now — a plan change or admin override is a rare action, not a hot path, and a per-process cache would reintroduce the exact cross-instance staleness bug already found and fixed in the moderation engine).
- Late-payment-after-expiry restoration (`handlePaystackWebhook`) uses a simplified rule: any signature-verified activation/renewal webhook restores an expired subscription to active. The stricter spec behavior — re-verifying against Paystack's own subscription-status API before restoring — is not yet implemented.

- The structured vendor Payment Method system (bank/cash type selection, admin-approval change requests, change history) is unbuilt and priced separately from Payment Requests — see the Payment requests & payment instructions section above for the distinction.
- AI Replies, AI Insights, and Auto-Accept-Orders all have their `PlanLimits` fields reserved and returned correctly today, but the underlying features themselves (an AI reply engine, automated order acceptance) do not exist yet — those are future-phase scope per the source spec's own table. - **Landing Page, CMS & Vendor Portal deferrals**, per `docs/LANDING_PAGE_CMS_VENDOR_PORTAL_MAPPING.md` Section 14: automated price-change notice enforcement (the 60-day notice period is an operational/manual process, not backend-enforced), automated notification workflow, full price versioning/audit history, a `pendingPriceChange` UI preview, and automated provider-side price migration tooling.
